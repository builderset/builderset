_This page describes Builderset 0.5.0._

At the end an ASP.NET Core app stores email templates, articles, forms, card designs
and popups with everything the [data model](/docs/guides/backend/data-model) asks of a
real app: who made, changed, published and deleted each row and when, a trash to
restore from, a revision on every manual save and publish, and an activity line for
everything that happens. It refuses an unsafe or stale save with the editor's own issue
codes, takes form responses and popup submissions checked exactly as the browser
checked them, and issues cards to members.

Tested with .NET 9 (SDK 9.0.321, ASP.NET Core 9.0.23) and C# 13, EF Core 9 with
Npgsql.EntityFrameworkCore.PostgreSQL 9.0.4 and EFCore.NamingConventions 9.0.0,
JsonSchema.Net 9.7.0, and PostgreSQL 18. About 25 minutes to read.

There is no Builderset package for C#, so every document is checked in two layers. Its
**structure** is checked in-process, against the kit's JSON Schema, with JsonSchema.Net.
The **kits' own rules** — an unsafe link, a variable the email type does not have, a
form's answers — run in the [Builderset checker](/docs/guides/backend/checker), a small
Node service beside the app that runs the same functions the editor runs. When the
checker cannot be reached, the app answers `503` and stores nothing.

The routes are minimal APIs grouped with `MapGroup`, not controllers: the five builders
share one set of routes over five row types, and a generic method mapped five times says
that directly, where controllers would need a generic controller and a feature provider
to register it.

```txt title="Builderset.Api/"
Builderset.Api.csproj   packages, and the kits' schemas copied in at build
Program.cs              services, middleware, route groups
Kinds.cs                what differs between the five builders
Data/                   the DbContext, and the interceptor that stamps who and when
Models/                 one file per group of tables
Auth/                   who is signed in: a stand-in for yours
Http/                   request records, problem details, the visitors' rate limit
Checks/                 the JSON Schemas, the checker's client, the two together
Audit/                  activity, revisions, soft delete and restore
Routes/                 documents, history, forms, cards, popups, library, delivery
Storage/                uploaded files on disk
```

### Forms and their responses

The public side takes no sign-in. The answers are checked by the checker against the
**published** document, never the draft; a filled trap field is answered as a success
and stored nowhere; and only the `values` that `validateAnswers` keeps are stored. The
count goes up in the same statement that checks `maxResponses`, so two visitors cannot
both take the last place. Your team's side lists the responses, triages them with
`PATCH` and deletes them softly; only your retention job deletes them for good.
