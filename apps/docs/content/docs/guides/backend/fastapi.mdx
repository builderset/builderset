_This page describes Builderset 0.4.0._

At the end a FastAPI app stores email templates, articles and forms, refuses an
unsafe or stale save with the same issue codes as the editor, and takes form
responses checked exactly as the form in the browser checked them. The tables and
routes are the ones in [Data model and API](/docs/guides/backend/data-model).
[FastAPI and SQLAlchemy](/docs/guides/backend/fastapi-sqlalchemy) is the complete,
tested backend for emails alone, with uploads, sending and its tests; this page
builds all three builders in the same style. The `builderset` package's install is in
[Python](/docs/reference/python).

### Saving a draft

The editor sends back the `saved_at` it last saw. A different one on the row means
someone else saved in between: `409`, and the editor offers to reload or keep its
own. The update is conditional, so two saves at the same instant cannot both win. The
column keeps milliseconds, as JavaScript does, so the value the editor sends back is
exactly the one stored:

<include cwd lang="python" meta='title="app/documents.py"'>
  ./snippets/backends/fastapi/documents.py#draft
</include>

</Step>
<Step>

### Publishing

The strict check, then the document goes live with its meta copied to the columns.
Publishing is its own permission. An email type keeps one active design; an article
with a future `scheduled_at` waits for a job of yours to set it live; a form's address
taken by another is refused on `meta.slug`, where the editor shows it:

<include cwd lang="python" meta='title="app/documents.py"'>
  ./snippets/backends/fastapi/documents.py#publish
</include>

Creating, reading, the list and unpublishing are in the same router. Unpublishing
leaves an email or an article a draft, and a form `closed`: its link keeps working
and shows the closed message. Revisions and saved sections have their models; their
routes are a list and an insert with the same check, and until you add them the
editor hides those features.

</Step>
<Step>

### The form's public routes

No sign-in. The answers are checked against the **published** document, never the
draft; a filled trap field is answered as a success and stored nowhere; and only the
`values` that `validate_answers` keeps are stored, so an answer to a question the
visitor was not shown never reaches the table. The count goes up in the same
statement that checks `maxResponses`, so two visitors cannot both take the last
place:

</Step>

### Uploads

An upload checks the file's type by its first bytes and its size, stores it under a
new key, and answers with the key and its address. The email example's
[upload route](/docs/guides/backend/fastapi-sqlalchemy#the-routes) is the one to copy;
here it would also write a `Media` row.

</Step>
