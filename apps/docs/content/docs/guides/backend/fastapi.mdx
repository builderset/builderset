_This page describes Builderset 0.4.0._

At the end a FastAPI app stores email templates, articles, forms, card designs and
popups with the whole audit trail of the [data model](/docs/guides/backend/data-model):
who made, changed, published and deleted each row and when, a revision on every manual
save and publish, and one activity line for everything that happens. It refuses an
unsafe or stale save with the same issue codes as the editor, deletes softly so a row
can be restored, takes form responses and popup submissions checked exactly as the
browser checked them, and issues cards to members.
[FastAPI and SQLAlchemy](/docs/guides/backend/fastapi-sqlalchemy) is the complete,
tested backend for emails alone; this page builds all five builders in the same
style. The `builderset` package's install is in [Python](/docs/reference/python).

The code is one package, `app`, with a file per concern. `app/__init__.py` and
`app/routers/__init__.py` are empty.

### Saving a draft

The editor sends back the `saved_at` it last saw. The update is filtered on it, so if
someone else saved in between it changes no row and the answer is `409`; the editor
offers to reload or keep its own. The column keeps milliseconds, as JavaScript does,
so the value the editor sends back is exactly the one stored. A manual save is kept
as a revision and logged; an autosave is neither:

<include cwd lang="python" meta='title="app/documents.py"'>
  ./snippets/backends/fastapi/app/documents.py#draft
</include>

</Step>

### Publishing

The strict check, then the document goes live with its meta copied to the columns,
in the order of [what each write does](/docs/guides/backend/data-model#what-each-write-does):
the row, a `publish` revision, a `published` line (and `renamed` when a name or slug
changed). An email type keeps one active design; an article with a future
`scheduled_at` waits for a job of yours to set it live; a form's address taken by
another is refused on `meta.slug`, where the editor shows it:

<include cwd lang="python" meta='title="app/documents.py"'>
  ./snippets/backends/fastapi/app/documents.py#publish
</include>

Publishing is usually its own permission: check it in `deps.py`'s stand-in.

### The form's public routes

No sign-in. The answers are checked against the **published** document, never the
draft; a filled trap field is answered as a success and stored nowhere; and only the
`values` that `validate_answers` keeps are stored, so an answer to a question the
visitor was not shown never reaches the table. The count goes up in the same
statement that checks `maxResponses`, so two visitors cannot both take the last
place. Your team triages responses with `PATCH` and deletes them softly; the
retention job is the one place a response is deleted for good:

### Cards

A card is issued from a published design only — `422` while it is a draft — and from
its live version: `fields_used` names the member's data it prints, every one is
required, and only those are frozen into the issue. The answer carries the card as it
is printed, the design filled in by `fill_card`. A member holds one card of a design
that is not revoked: the partial unique index `card_issue_one_valid` refuses a second,
answered `409`. Revoking keeps the row, so the number printed on the card still points
at it:

  ./snippets/backends/fastapi/app/routers/cards.py

### Popups

Your site asks which popups may show on a page; the server answers from the indexed
columns, the dates, then the page and language rules with the kit's `path_matches` and
`language_matches`, highest priority first. `should_show` — `shouldShow` in the
browser — decides the rest: the audience, how often, the device. Events add to the
day's counters in one upsert; a submission is checked with `validate_submission`
against the live popup, and only its `values` are stored. Pausing takes `{ paused }`
and changes only the status, so the document and `saved_at` stay as they are; a draft
answers `409`:

  ./snippets/backends/fastapi/app/routers/popups.py
</include>
