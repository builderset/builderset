description: The five builders' backend in Java — Spring Boot 3 with Spring Data JPA over Postgres, Flyway running the SQL schema, every row audited and soft-deleted, revisions and an activity log written in the same transaction, documents checked by the kits' JSON Schemas and the Builderset checker.

_This page describes Builderset 0.5.0._

At the end a Spring Boot app stores email templates, articles, forms, card designs and
popups with everything the [data model](/docs/guides/backend/data-model) asks of a real
app: who made, changed, published and deleted each row and when, a trash to restore
from, a revision on every manual save and publish, and an activity line for everything
that happens. It refuses an unsafe or stale save with the editor's own issue codes,
takes form responses and popup submissions checked exactly as the browser checked
them, and issues cards to members.

Tested with Spring Boot 3.5.7 on Java 21 (Temurin 21.0.12, Maven 3.9), with
Hibernate 6.6, Spring Data JPA 3.5, Flyway 11.7, networknt json-schema-validator 1.5.8
and PostgreSQL 18. About 30 minutes to read.

There is no Builderset package for Java, so every document is checked in two layers.
Its **structure** is checked in-process, against the kit's JSON Schema. The **kits' own
rules** — an unsafe link, a variable the email type does not have, a form's answers —
run in the [Builderset checker](/docs/guides/backend/checker), a small Node service
beside the app that runs the same functions the editor runs. When the checker cannot
be reached, the app answers `503` and stores nothing.

The tables are the [SQL schema](/docs/guides/backend/sql)'s own files, run by Flyway;
the entities are mapped onto them and Hibernate only checks that they match. Code is
grouped by feature, one package per builder:

```txt title="src/main/java/com/example/builder/"
Application.java   the app
shared/            the audit columns, the document columns, revisions, people, statuses
audit/             who is signed in (a stand-in for yours), auditing, the trash
web/               errors as answers, paging, the sign-in check, uploaded files
checks/            the JSON Schemas, the checker's client, the two together
activity/          the activity log
documents/         the routes the five builders share, written once
emails/ articles/ forms/ cards/ popups/   each builder: its tables, and what is its own
library/           saved sections and uploads
```

<include cwd lang="sh" meta='title="migrations.sh"'>
  ./snippets/backends/spring-boot/migrations.sh
</include>

Flyway runs them in order on startup, and with `ddl-auto=validate` Hibernate refuses to
start when an entity names a column the tables do not have. The partial unique
indexes, the triggers that keep `updated_at` and the check constraints are the SQL's,
so they hold whatever writes to the tables.

### The models

One package per group of tables. Every entity extends one of two `@MappedSuperclass`es:
the audit columns, or the audit columns and a document. Spring Data's auditing fills
`created_by` and `updated_by` from the signed-in user; deleting stamps `deleted_at` and
`deleted_by` and keeps the row. The database spells statuses in lowercase — `draft`,
`status_changed` — so each enum carries a converter that writes them so.

### The library

Saved sections, per builder — email, article and form; cards and popups keep none —
and uploads. A section's nodes are held to the kit's element rules by the same JSON
Schema as a document's. A file is known by its first bytes, never by its name, and the
