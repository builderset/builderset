_This page describes Builderset 0.4.0._

At the end your Supabase project stores email templates, articles and forms, refuses
an unsafe or stale save with the editor's own issue codes, and takes form responses
from visitors who cannot write to any table. The tables are the ones in
[Data model and API](/docs/guides/backend/data-model). The checks are the kits' own,
so they run where JavaScript runs: in two Edge Functions. A policy cannot run them,
so no document reaches a table except through a function.

<Steps>
<Step>

### The tables, and who may read them

One migration: the [SQL schema](/docs/guides/backend/sql) with uuid ids and
Supabase's users, row-level security on every table, the function that stores a
response, and the media bucket. Put it in `supabase/migrations/` and run
`supabase db push`:

<include cwd lang="sql" meta='title="supabase/migrations/0001_builderset.sql"'>
  ./snippets/backends/supabase/migrations/0001_builderset.sql
</include>

Three choices in it:

- **The team is a table, not the author.** A row in `profiles` makes a user an
  `editor` or a `publisher`. A policy of `auth.uid() = created_by` would let only a
  template's author fix a typo in it. With one team per project, membership is the
  rule; with several, add a `team_id` to `profiles` and to each table, and compare
  the two in the same policies. You add members yourself, from the dashboard or SQL.
- **Nobody writes through the REST API.** The team may read every row, for lists and
  search; there is no insert or update policy, so only the service role writes, and
  only the functions below hold it, after their checks.
- **The public reads columns, not tables.** `anon` may select the live `document` of
  a published article or form, and nothing else: it must name the columns
  (`select=id,slug,status,document`), and a `draft_document` is never theirs, even of
  a published row. It cannot insert into `form_response` at all.

</Step>

<Step>

### The form's public routes

The page that shows a form reads it through the REST API with the anon key, and
passes `closed` to `FormView` when its `status` is `closed`. A response goes to its
own function, which reads the **published** document with the service role, ignores
a filled trap field, checks the answers with `validateAnswers`, and stores only the
`values` it keeps. `record_form_response` in the migration counts and stores in one
transaction, so `maxResponses` holds when two visitors send the last response at once:

<include cwd lang="ts" meta='title="supabase/functions/form-responses/index.ts"'>
  ./snippets/backends/supabase/functions/form-responses/index.ts
</include>

Deploy it with `supabase functions deploy form-responses`. It has no rate limit; the
`429` of the data model needs a counter by address, in a table or at your edge.

</Step>
<Step>

### Uploads

The `media` bucket is public, so a published page shows its images at an address that
never changes, and Storage enforces the bucket's size and type limits on the server.
The editor uploads straight into it, into the user's own folder (the policy refuses
any other), and keeps the object's key in the document. Storage's own
`storage.objects` holds each file's key, size, type and owner, so there is no `media`
table. Files a visitor attaches to a form response need a signed upload URL from a
function, which is not shown here.

</Step>
