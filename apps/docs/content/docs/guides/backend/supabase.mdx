_This page describes Builderset 0.4.0._

At the end your Supabase project stores email templates, articles and forms with who
made, changed and deleted every row, keeps their revisions and an activity log,
refuses an unsafe or stale save with the editor's own issue codes, and takes form
responses from visitors who cannot write to any table. The tables are the ones in
[Data model and API](/docs/guides/backend/data-model), with Supabase's own users. The
checks are the kits' own, so they run where JavaScript runs: in two Edge Functions. A
policy cannot run them, so no document reaches a table except through a function.

Four choices in them:

- **The team is a table, not the author.** A row in `profiles` makes a user an
  `editor` or a `publisher`. A policy of `auth.uid() = created_by` would let only a
  template's author fix a typo in it. With one team per project, membership is the
  rule; with several, add a `team_id` to `profiles` and to each table, and compare the
  two in the same policies. You add members yourself, from the dashboard or SQL.
- **The functions name the actor.** A write made with a user's token carries
  `auth.uid()`, and the `stamp_actor` trigger puts it in `created_by` and `updated_by`
  whatever the request said. The Edge Functions write with the service role, which has
  no user, so `auth.uid()` is null there: they check the caller's token themselves and
  pass that user to every write function as `p_actor`.
- **Nobody writes through the REST API.** The team may read every row, live or in the
  trash, for lists and search; there is no insert, update or delete policy, and the
  grants are gone too, so only the service role writes. Even it may not change the
  activity log or a revision.
- **The public reads columns, not tables.** `anon` may select the live `document` of a
  published article or form, and nothing else: it must name the columns
  (`select=uuid,slug,document`), and a `draft_document`, the internal `id` or who wrote
  it is never theirs. It cannot insert into `form_response` at all.

Scheduled articles go live when `publish_due_articles()` runs: schedule it every
minute with `pg_cron`. The retention job that deletes old responses for good is
yours too; it is the one place a row is removed.

### The form's public routes

The page that shows a form reads it through the REST API with the anon key, and passes
`closed` to `FormView` when its `status` is `closed`. A response goes to its own
function, which reads the **published** document with the service role, ignores a
filled trap field, checks the answers with `validateAnswers`, and stores only the
`values` it keeps. `record_form_response` counts and stores in one transaction, so
`maxResponses` holds when two visitors send the last response at once:

<include cwd lang="ts" meta='title="supabase/functions/form-responses/index.ts"'>
  ./snippets/backends/supabase/functions/form-responses/index.ts
</include>

Deploy it with `supabase functions deploy form-responses`. It has no rate limit; the
`429` of the data model needs a counter by address, in a table or at your edge.

</Step>
<Step>

### Uploads

The `media` bucket is public, so a published page shows its images at an address that
never changes, and Storage enforces the bucket's size and type limits on the server.
The editor sends a file to the documents function, not to Storage: there is no policy
on `storage.objects`, so only the function, after reading the file's first bytes,
puts it there. The `media` table keeps what Storage does not know — the kind, an
image's size, who uploaded it and a hash — and documents keep only the key. A deleted
file stays in the bucket until a job of yours removes the ones no live document uses.

</Step>
