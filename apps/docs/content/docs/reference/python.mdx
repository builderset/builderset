_This page describes Builderset 0.4.0._

`builderset` is the server side of the kits in Python. It checks an article, an
email or a form with the same rules and the same issue codes as the TypeScript
packages, checks a form's answers exactly as the browser did, and renders an email to
the same HTML and text, byte for byte: the email you send is the one the editor
showed. Python 3.11 or newer.

## Install

Until Builderset is public, the wheel is attached to each GitHub release
(`v0.4.0`, beside its SHA-256). Download it and install the file:

## Check and render an email

<include cwd lang="python" meta='title="send_email.py"'>
  ./snippets/python/send_email.py
</include>

- `check_email(document, spec, *, locales, check_media_key)` — every reason the
  template cannot be stored. `spec` is the template's email type: its variables, the
  ones it must use, and whether it is marketing (then it needs an unsubscribe link).
- `render_email(document, *, asset_url, brand, data, locale, currency)` — the subject,
  preheader, HTML and plain text.

## Articles

`builderset.article.check_article(document, *, locales, check_media_key)` checks an
article. There is no article renderer in Python: it is React. A Python site serves
the document to a JavaScript front end, or renders it with its own templates.

## Forms

`builderset.form` checks the form a person builds and the answers a visitor sends.

<include cwd lang="python" meta='title="check_form.py"'>
  ./snippets/python/check_form.py
</include>

- `check_form(document, *, locales, check_media_key)` — every issue `checkForm`
  reports, with the same codes. Some are warnings (`is_warning`): worth showing, never
  a reason to refuse. A draft may still carry the codes in `DRAFT_TOLERATES`
  (`is_draft_blocking`); going live refuses every error (`is_publish_blocking`).
- `validate_answers(document, answers, *, step)` — the answers checked exactly as the
  form checked them in the browser: which fields show, which must be answered, what
  each answer must look like. `result.errors` holds, per field key, the first thing
  wrong (`code`, and `limit` or `message` when there is one); `result.values` holds
  the answers worth storing — shown fields only, numbers as numbers. `as_dict()` gives
  the shape `validateAnswers` returns.

A form's own pattern (`checks.regex`) is compiled by Python's `re`, not by
JavaScript. The two agree on what people write for a plate or a code; on exotic
syntax (`\p{…}`, variable-length lookbehind) one of them may refuse what the other
takes.

## Media keys are your rule

Which storage keys exist, and which a document may use, is your application's
business. Pass `check_media_key`: a function that returns `None` for an allowed key
and an issue code (`media.invalidKey`, `media.wrongFolder`) otherwise. Without one,
keys are checked for their shape only.

## Dates and numbers

`{{ value | date }}`, `| money` and `| number` are formatted in `sq`, `en` and `de`;
any other language is formatted as English, in the `Europe/Tirane` time zone — as in
the TypeScript renderer, so both still agree byte for byte.
