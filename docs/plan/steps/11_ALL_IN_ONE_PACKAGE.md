# 11 — The all-in-one package

## Goal

`builderset` is one package that contains every kit. A developer who wants everything installs one name; a developer who wants one builder still installs only that kit.

```bash
npm install builderset              # everything
npm install @builderset/email       # only the email builder
```

## Why

- A project that uses two or three kits should not manage two or three version numbers.
- Two kit stylesheets each contain the engine's rules. `builderset/styles.css` contains each rule once.
- One name is easier to find, to say and to write in a tutorial.

It adds no code of its own. It is a set of re-exports and one stylesheet.

## Before you start

- Step 09 is done. Step 10 is needed for the stylesheet part only.

## The work

### 1. The package

```
packages/builderset/
├── src/
│   ├── engine/          index.ts  editor.ts  ui.ts  host.ts
│   ├── email/           index.ts  render.ts  editor.ts  host.ts
│   ├── article/         index.ts  render.ts  editor.ts  host.ts
│   ├── locales/         en.ts  sq.ts  de.ts
│   └── styles.css
├── scripts/generate.mjs
├── package.json
└── README.md
```

### 2. The re-export files are generated

Each file re-exports one door of one package. Do not write them by hand: a name added to a kit and forgotten here is a bug nobody notices until a user reports it.

`scripts/generate.mjs` reads each package's built type file (`dist/<door>/index.d.ts`), collects its exported names, and writes:

```ts
// src/email/editor.ts — generated by scripts/generate.mjs. Do not edit.
'use client';

export { EmailCanvas, EmailEditor, emailProfile } from '@builderset/email/editor';
export type {
  EmailCanvasProps,
  EmailEditorProps,
  EmailProfileOptions,
} from '@builderset/email/editor';
```

Rules for the generator:

- **Named exports, never `export *`.** The files for client doors (`editor`, `ui`) start with `'use client'`, and Next.js refuses `export *` in a client boundary.
- **Types are re-exported with `export type`.**
- **Server doors get no directive**: `index.ts`, `render.ts`, `host.ts`.
- The generator runs before the build (`"prebuild": "node scripts/generate.mjs"`), and a test fails if running it changes any committed file.

### 3. Locales

A locale file that holds every kit's words for one language:

```ts
// src/locales/sq.ts — generated.
import article from '@builderset/article/locales/sq';
import email from '@builderset/email/locales/sq';

export default { ...email, ...article, code: 'sq' };
```

Check the shape against step 05: the engine's words are the same object in both kits, so the spread loses nothing.

### 4. The stylesheet

`src/styles.css` is the engine's theme with every kit's source folders, compiled once:

```css
@import '../../engine/src/theme/index.css';

@source '../../engine/src/editor';
@source '../../email/src/editor';
@source '../../article/src/editor';
@source '../../article/src/render';
```

`builderset/styles.css` therefore covers every editor and the rendered article. A site that only shows articles should still use `@builderset/article/content.css` or `builderset/article/content.css`, which is much smaller; re-export that file too.

**There is no `"."` entry.** `import { EmailEditor } from 'builderset'` must not work. A root entry would have to be either a client or a server module, and the product has both: the path is what says which side the code is for. A developer who tries it gets "Package subpath '.' is not defined by exports"; the README's first example shows the right form.

Schema and fixture files are not re-exported. A backend that needs them depends on the kit.

### 6. When a kit is added

Popup, page and form each add: a folder under `src/`, a block in `exports`, a `@source` line, a dependency. Put that in the recipe ([19_ADDING_A_NEW_BUILDER.md](19_ADDING_A_NEW_BUILDER.md)) — it is the step people forget.

### 7. The README

Short, because it is the first thing shown on the registry:

1. What the product is, in two sentences, and a picture of an editor.
2. `npm install builderset`, and the note that each kit can be installed alone.
3. An editor in ten lines and a render in five.
4. The table of kits with their separate package names.
5. A link to the docs site.

## Check

```bash
pnpm build && pnpm check:packages
node --input-type=module -e "
  const { renderEmail } = await import('builderset/email/render');
  const { createArticleRegistry } = await import('builderset/article');
  console.log(typeof renderEmail, typeof createArticleRegistry);
"
node --input-type=module -e "await import('builderset')" ; echo "exit code $? (must not be 0)"
```

In the Next example: one page imports `EmailEditor` from `builderset/email/editor`, another renders an article in a Server Component from `builderset/article/render`. `next build` passes, and the article page's client JavaScript does not contain the editor.

- [x] `packages/builderset` builds; every door of every kit is re-exported.
- [x] The re-export files are generated, and a test fails when they are stale.
- [x] Client doors start with `'use client'` and use named exports.
- [x] `import 'builderset'` fails; every sub-path imports.
- [x] `builderset/styles.css` contains each rule once and is smaller than the kit stylesheets added together.
- [x] `publint` and `attw` pass.
- [ ] The Next example builds with imports from `builderset/…`.

## Traps

- **A hand-edited generated file.** The next build overwrites it. The header says so; the staleness test enforces it.
- **A type-only export re-exported as a value.** With `verbatimModuleSyntax` it is a build error; without it, a run-time "does not provide an export named". Generate `export type` for types.
- **Two engines.** If `builderset` and a separately installed `@builderset/email` are at different versions, the project has two engines. Each editor still works, since an editor uses only its own engine, but the bundle doubles. The engine records its version on `globalThis` when it loads and logs one warning in development if a second, different version loads.
- **Offering both and explaining neither.** The README of every kit must say "also available inside `builderset`", and the README of `builderset` must say each kit installs alone. Otherwise people install both.
